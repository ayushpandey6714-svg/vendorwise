# Architecture: how to explain the code

## 1. A schema is a contract

`schemas.py` defines a `Fact[T]`: value, explicit/missing/ambiguous status, and source passages. For example, RAM can be an explicit integer 16 with page evidence, or missing with `None`. Pydantic rejects an explicit fact without evidence and rejects an invented value on a missing fact. Unknown money is distinct from an explicit `Decimal("0")`.

The model produces structured data conforming to `Extraction`. `pdf.validate_provenance` additionally verifies the document identity, page range and whitespace-normalized source substring. This second check catches fabricated source text, but cannot decide whether a real sentence was interpreted correctly.

## 2. The business core is a pure function

`audit_quote(quote)` produces vendor-stated total, independently calculated total, completeness, discrepancy, comparability, audit steps and source inputs. Discount, tax, shipping and other charges must have explicit bases and inclusions. Tax can be a fixed amount or a percentage of a supported base. Included components are not added twice. All calculations use Decimal with a declared rounding rule.

`compare(quotes, requirements)` creates six checks per offer. FAIL takes precedence over UNKNOWN; an offer with neither is PASS. Verified price is a separate gate. The cheapest eligible offer is recommended; equal prices return a tie. An unresolved offer without a definitive exclusion makes the result provisional.

`what_if` creates the updated requirements by replacing only budget, warranty and delivery. It calls the same `compare` function twice, explains changed checks and subtracts verified winner costs when both exist. It cannot change quoted quantities or use a model to renegotiate prices.

## 3. Extraction and retrieval solve different problems

Extraction interprets an entire small quotation into structured facts. RAG answers a particular question using relevant page passages. `chunk_documents` cuts each actual PDF page separately, retaining UUID, filename and page. FastEmbed produces local BGE semantic vectors; Qdrant stores them on disk. A question is embedded locally, searched with document filters, and the retrieved passages are sent to the live answer model.

TF-IDF is a second, explicitly selected local lexical vector baseline for a download-free demo. It fits vocabulary within the analysis and reconstructs it deterministically from stored chunks. It does not claim synonym-level semantic understanding. Both backends use the same Qdrant store and citation machinery.

## 4. Tool calls are proposals, not trusted facts

The live model can propose only three functions. Their argument schemas allow search strings and document IDs, not prices or new requirements. `ToolRunner` looks up server-owned quotations in the current analysis. Invalid arguments and unknown IDs produce explicit tool errors. The model has at most four executions to gather information, then it must produce a structured answer.

The server validates every citation ID against chunks actually retrieved in that request. The returned snippet is taken from stored PDF text, not generated by the model. Calculations are returned separately with their original source inputs. The UI logs concise real tool outcomes, not chain-of-thought.

## 5. State and boundaries

Streamlit handles forms, tables and session state. FastAPI owns validation and logic. A UUID directory holds each analysis JSON, raw PDFs and a separate Qdrant index. Atomic JSON replacement prevents readers seeing half-written state. A process lock serializes mutation and Qdrant access. This is deliberately one local process/worker; UUID isolation does not authenticate a user.

Configuration comes from environment variables and a local `.env`; keys stay in the backend. The UI can observe only a configured/not-configured flag. Nothing sends email, buys a product or deploys services.

Every outbound model request passes through `Provider.call`, which atomically reserves a slot in a SQLite rolling-minute and rolling-24-hour budget. Failed calls and explicit schema-repair attempts count too; SDK automatic retries are disabled. Budgets are shared across visitors and persist as long as the data directory does. They are not authentication or monetary limits. Separate sample-only mode rejects arbitrary uploads before parsing. Live mode preserves uploads with a bounded analysis count.

## 6. What to improve after the current scope

Collect permissioned, diverse quotations and independent field labels; measure live extraction and answer support before changing prompts. Add clause-level conflict checks and field review/edit workflows if evidence justifies them. Benchmark chunk sizes on the development subset, then evaluate new unseen cases. Avoid adding agents or weighted rankings merely to increase the feature count.
